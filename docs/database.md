# Database Documentation

Personal Learner uses **Microsoft SQL Server** as its database, connected via SQLAlchemy's async engine using `aioodbc` + `pyodbc` with ODBC Driver 18.

---

## Why MS SQL Server?

The project was initially planned for PostgreSQL but switched to MS SQL Server for local development compatibility. SQL Server runs natively on Windows and can also be containerized via Docker for cross-platform development.

---

## Database Setup

### The SQL Script (`table_schema.sql`)

The root-level `table_schema.sql` file contains the complete DDL for creating the database and all tables from scratch. Key points:

- Database name: `personal_learner`
- All primary keys use `UNIQUEIDENTIFIER` with `DEFAULT NEWID()`
- Foreign keys use `ON DELETE CASCADE` where appropriate to maintain referential integrity
- `NVARCHAR(MAX)` replaces PostgreSQL's `TEXT` type
- `BIT` replaces PostgreSQL's `BOOLEAN` type
- `DATETIME2` is used for all timestamps (higher precision than `DATETIME`)
- A seed `INSERT` creates a default user for development

## Table: `users`

The users table is intentionally minimal for the MVP — there's no authentication, password hashing, or session management. A single user is seeded for development.

```sql
CREATE TABLE users (
    id          UNIQUEIDENTIFIER PRIMARY KEY DEFAULT NEWID(),
    username    VARCHAR(50)  UNIQUE NOT NULL,
    email       VARCHAR(255) UNIQUE NOT NULL,
    created_at  DATETIME2    DEFAULT CURRENT_TIMESTAMP
);
```

**Seed data:**
```sql
INSERT INTO users (id, username, email) 
VALUES ('c2b27bf8-40d5-4015-9023-7aea7c615495', 'Prasun', 'prasun03.work@gmail.com');
```

This UUID is hardcoded in the frontend's `.env.local` as `NEXT_PUBLIC_DEFAULT_USER_ID`.

**Relationships:**
- One user has many topics (`topics.user_id` → `users.id`, CASCADE delete)
- One user has many flashcards (`flashcards.user_id` → `users.id`)
- One user has many review logs (`review_logs.user_id` → `users.id`)
- One user has many topic proficiencies (`topic_proficiency.user_id` → `users.id`)

## Table: `topics`

Represents a learning subject or Obsidian vault note.

```sql
CREATE TABLE topics (
    id                  UNIQUEIDENTIFIER PRIMARY KEY DEFAULT NEWID(),
    user_id             UNIQUEIDENTIFIER NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    name                VARCHAR(100) NOT NULL,
    obsidian_file_path  VARCHAR(255),
    created_at          DATETIME2 DEFAULT CURRENT_TIMESTAMP,
    UNIQUE(user_id, name)
);
```

**Constraints:**
- `UNIQUE(user_id, name)`: A user cannot have two topics with the same name (e.g., two "Docker" topics)
- `ON DELETE CASCADE` on `user_id`: Deleting a user deletes all their topics (and cascades to flashcards, review logs, proficiencies)

**Relationships:**
- Belongs to one user (`user_id` FK)
- Has many flashcards (`flashcards.topic_id` → `topics.id`, CASCADE delete)
- Has many topic proficiencies (`topic_proficiency.topic_id` → `topics.id`, CASCADE delete)

**`obsidian_file_path`**: Stores the relative or absolute path to the originating Obsidian note. Currently informational — not used for sync logic.

## Table: `flashcards`

The core table. Each row is one flashcard generated by the AI or manually created.

```sql
CREATE TABLE flashcards (
    id                UNIQUEIDENTIFIER PRIMARY KEY DEFAULT NEWID(),
    user_id           UNIQUEIDENTIFIER NOT NULL REFERENCES users(id),
    topic_id          UNIQUEIDENTIFIER NOT NULL REFERENCES topics(id) ON DELETE CASCADE,

    -- Card metadata
    card_type         VARCHAR(20) NOT NULL,           -- 'standard' or 'code_mcq'
    difficulty_level  INT DEFAULT 1,                  -- 1 (Beginner) to 5 (Advanced)

    -- Content
    front_content     NVARCHAR(MAX) NOT NULL,          -- Question or code snippet
    back_content      NVARCHAR(MAX) NOT NULL,          -- Answer or explanation
    extra_data        NVARCHAR(MAX),                   -- JSON: MCQ options, language, etc.

    -- Spaced Repetition (SM-2)
    repetition_count  INT DEFAULT 0,
    interval_days     FLOAT DEFAULT 0,
    ease_factor       FLOAT DEFAULT 2.5,
    next_review_date  DATETIME2 DEFAULT CURRENT_TIMESTAMP,

    -- Timestamps
    created_at        DATETIME2 DEFAULT CURRENT_TIMESTAMP,
    updated_at        DATETIME2 DEFAULT CURRENT_TIMESTAMP
);
```

### `card_type` Values

| Value | Front Content | Back Content | `extra_data` |
|---|---|---|---|
| `standard` | Question text | Answer text | `null` |
| `code_mcq` | Code snippet | Correct answer text | JSON with `language`, `options[]`, `correct_index`, `explanation` |

### `extra_data` JSON Structure (for `code_mcq`)

```json
{
  "language": "python",
  "options": [
    "Error: cannot multiply string by int",
    "'aa'",
    "'a2'",
    "2"
  ],
  "correct_index": 1,
  "explanation": "In Python, the * operator on a string repeats it. 'a' * 2 produces 'aa'."
}
```

**Note:** In MS SQL Server, `extra_data` is stored as `NVARCHAR(MAX)` (a text column), not a native JSON type. SQLAlchemy's `JSON` column type handles serialization/deserialization transparently. The application treats it as JSON but the database stores it as a string.

### SM-2 Spaced Repetition Fields

| Field | Initial Value | Range | Description |
|---|---|---|---|
| `repetition_count` | `0` | `0` to ∞ | Number of consecutive correct (grade ≥ 3) reviews |
| `interval_days` | `0` | `0` to ∞ | Days until next review; `0` = immediately due |
| `ease_factor` | `2.5` | `1.3` to ∞ | SuperMemo-2 ease factor; adjusts based on grade |
| `next_review_date` | `CURRENT_TIMESTAMP` | — | When this card becomes due; `≤ now` = due |

### Index

```sql
CREATE INDEX idx_flashcards_next_review ON flashcards(user_id, next_review_date);
```

This composite index optimizes the most frequent query: "Get all due cards for a user." The `user_id` prefix filters to one user's data, and `next_review_date` enables efficient range scans for `next_review_date <= now`.

### Card Lifecycle

```
Created (SM-2: interval=0, ease=2.5, reps=0, due=now)
    │
    ▼
Due (appears in review queue)
    │
    ▼
Reviewed with grade 1-2 (Again/Hard)
    │  → reps reset to 0, interval → 1 day
    ▼
Due again in 1 day
    │
    ▼
Reviewed with grade 3-4 (Good/Easy)
    │  → reps++, interval increases (1→6→interval*ease)
    ▼
Due later (days/weeks/months)
    │
    ▼
Reviewed repeatedly until reps ≥ 4
    │  → Considered "mastered" (counts toward topic proficiency)
    ▼
Mastered (long review intervals — may be months)
```

## Table: `review_logs`

An append-only log of every review action. Used for analytics, progress tracking, and the dashboard heatmap.

```sql
CREATE TABLE review_logs (
    id                UNIQUEIDENTIFIER PRIMARY KEY DEFAULT NEWID(),
    flashcard_id      UNIQUEIDENTIFIER NOT NULL REFERENCES flashcards(id) ON DELETE CASCADE,
    user_id           UNIQUEIDENTIFIER NOT NULL REFERENCES users(id),
    grade             INT NOT NULL,                    -- 1 (Again) to 4 (Easy)
    review_duration_ms INT,                             -- Time spent reviewing (future use)
    reviewed_at       DATETIME2 DEFAULT CURRENT_TIMESTAMP
);
```

**Note on `user_id` FK:** Uses `users(id)` without `ON DELETE CASCADE` to avoid circular cascade conflicts. The `flashcard_id` FK already cascades on delete (flashcard → review_log), and the user FK is denormalized for query convenience.

**Used by:**
- `GET /api/users/{user_id}/progress` — Groups by date to build the heatmap
- Future analytics: average grade per topic, review velocity, time-of-day patterns

## Table: `topic_proficiency`

Aggregated mastery stats per user per topic. **Recalculated after every review submission.**

```sql
CREATE TABLE topic_proficiency (
    id                        UNIQUEIDENTIFIER PRIMARY KEY DEFAULT NEWID(),
    user_id                   UNIQUEIDENTIFIER NOT NULL REFERENCES users(id),
    topic_id                  UNIQUEIDENTIFIER NOT NULL REFERENCES topics(id) ON DELETE CASCADE,
    mastery_score             FLOAT DEFAULT 0.0,         -- 0.0 to 100.0
    cards_mastered            INT DEFAULT 0,             -- Cards with reps ≥ 4
    needs_remedial_material   BIT DEFAULT 0,             -- AI intervention flag (future)
    ready_for_advanced        BIT DEFAULT 0,             -- Advanced content flag (future)
    last_evaluated_at         DATETIME2 DEFAULT CURRENT_TIMESTAMP,
    UNIQUE(user_id, topic_id)
);
```

### Mastery Score Calculation

Recalculated on every `PATCH /api/review/{flashcard_id}`:

```python
# For each card in the topic:
card_mastery = min(100.0, repetition_count * 25.0)

# Overall mastery = average of all card masteries
mastery_score = sum(card_mastery for all cards) / total_cards
```

This means:
- A card with 0 correct reviews contributes 0%
- A card with 4 correct reviews contributes 100% (and is considered "mastered")
- The overall score is the mean across all cards in the topic

### Future Flags

- `needs_remedial_material`: When set to `1`, future background tasks could trigger the LLM to generate remedial study guides and write them back to Obsidian
- `ready_for_advanced`: When set to `1`, could trigger generation of higher-difficulty cards or prompt the user to explore advanced material

## ORM Notes

### SQLAlchemy Models (`app/models/models.py`)

The ORM models closely mirror the SQL schema with a few key differences:

1. **`extra_data` column**: Declared as `Column(JSON)` in SQLAlchemy, which handles Python dict ↔ JSON string conversion. MS SQL stores it as `NVARCHAR(MAX)` under the hood.

2. **Computed property**: `Flashcard.topic_name` does `self.topic.name if self.topic else ""`. This requires eager loading (`selectinload(Flashcard.topic)`) in queries that use it.

3. **Server defaults**: Many columns use `server_default=text("CURRENT_TIMESTAMP")` or `server_default=text("NEWID()")`. These are applied by MS SQL Server, not by SQLAlchemy — the ORM just knows to expect them.

4. **`Uuid(as_uuid=True)`**: Ensures Python `uuid.UUID` objects are used, not strings.

### Relationship Loading Strategy

- `Flashcard.topic`: Uses `selectinload()` in the due-cards endpoint (eager loads topic to avoid N+1 queries for `topic_name`)
- Other relationships use lazy loading (default in SQLAlchemy async)

## Query Patterns

### Most Common Query: Get Due Cards

```python
stmt = select(Flashcard).options(selectinload(Flashcard.topic)).where(
    Flashcard.user_id == user_id,
    Flashcard.next_review_date <= now
).order_by(Flashcard.next_review_date)
```

Efficiently utilizes `idx_flashcards_next_review` index.

### Dashboard Aggregation Query

```python
select(
    Topic,
    func.coalesce(TopicProficiency.mastery_score, 0.0),
    func.count(Flashcard.id),
    func.sum(func.iif(Flashcard.next_review_date <= now, 1, 0)),
).outerjoin(TopicProficiency, ...).outerjoin(Flashcard, ...).where(
    Topic.user_id == user_id
).group_by(Topic.id, ...)
```

Uses `func.iif` (MS SQL's conditional) to count due cards inline without a subquery.

### Progress Heatmap Query

```python
select(
    cast(ReviewLog.reviewed_at, Date).label("review_date"),
    func.count(ReviewLog.id).label("count")
).where(
    ReviewLog.user_id == user_id
).group_by(cast(ReviewLog.reviewed_at, Date))
```

Groups by date (stripping time) to get daily review counts. Uses `CAST` to `Date` type.
